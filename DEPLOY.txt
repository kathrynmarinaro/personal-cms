PERSONAL CRM — DEPLOY CHECKLIST
===============================

PHP + MySQL, no build step. Three tabs: Today, People, Add.
Rebuild this bundle any time with:  php tools/build-deploy.php

Long-form reasoning for every decision below lives in the repo, in
CLAUDE.md and docs/PLAN.md. This file is the checklist.


FILE LAYOUT
-----------

Upload the CONTENTS of this bundle into the folder your (sub)domain
points at, e.g. public_html/crm/ :

    .htaccess     the document-root shim. MUST be present
    config.php    you create this in step 2
    schema.sql
    lib/          includes lib/vendor/PHPMailer (3 files)
    tools/
    uploads/      must exist, must stay denied
    public/       the app's public files

  >> The folder MUST be called public — NOT public_html. The shim
     rewrites into it by name. Rename it and you get a bare 404 with
     nothing in any log.
  >> Turn on SHOW HIDDEN FILES before and after uploading. There are
     FOUR .htaccess files: ./ lib/ tools/ uploads/ . Miss one and the
     site still works perfectly while your config is downloadable.
  >> Check uploads/.htaccess twice. An uploaded .vcf is the name, phone,
     email and home address of everyone in your phone, in plain text.
  >> Delete Hostinger's default.php placeholder if present.


1. DATABASE
-----------

  [ ] hPanel -> Databases -> create database + user
      >> Hostinger prefixes both with your account id: u123456_crm
  [ ] hPanel -> phpMyAdmin -> Import -> schema.sql
      Creates 10 tables. Seeds only the 5 relationship tags. Starts empty.


2. CONFIG
---------

  [ ] Rename config.example.php -> config.php
  [ ] Fill the db block. Host stays 'localhost'
  [ ] Set 'timezone' to a NAMED zone you live in (defaults America/Chicago)
      >> Highest-consequence value in the file. The whole app is dates,
         and PHP's and MySQL's defaults are set independently. A one-day
         skew = birthday cards late, every time, silently.
  [ ] php tools/make-hash.php -> paste output as 'password_hash'
      >> DO THIS BEFORE POINTING A DOMAIN AT THE APP. Left as CHANGE_ME
         the gate FAILS OPEN and every screen is public. Deliberate — an
         app with no hash can't authenticate anyone, so refusing entry
         would lock YOU out. But this database is everyone you know,
         their home addresses and their birthdays. Set it first.
  [ ] Optional: 'app_url' => 'https://crm.example.com'
      Without it, a command cron's emails name the profile screen
      instead of linking to it. Nothing else changes.


3. EMAIL
--------

  [ ] 2FA on the Google account (no 2FA, no app passwords)
  [ ] Get an app password: https://myaccount.google.com/apppasswords
      >> Google REMOVED this link from the 2-Step Verification page. Go
         to the URL directly. The feature is alive; only the link is gone.
      >> Shown exactly once. Copy it before closing the dialog.
      >> NOT the account password — Google stopped accepting those for
         SMTP in 2022. Fails as "Username and Password not accepted".
  [ ] Fill the smtp block:
          'user'       => 'you@gmail.com'
          'pass'       => the 16-char APP PASSWORD (spaces optional)
          'from_email' => 'you@gmail.com'   <- MUST EQUAL 'user'
          'to'         => 'you@gmail.com'   <- where reminders go
      >> from_email != user is the #1 failure and the only one that looks
         like success from inside the app: Gmail silently rewrites or
         rejects, the app records a delivery, no mail arrives.
         send-test-email.php refuses to send if they disagree.
  [ ] php tools/send-test-email.php   (from the folder holding lib/)
  [ ] Check your phone. Not there in a minute? Check spam — whatever you
      do with the first message is what Gmail learns for all the rest.


4. THE CRON
-----------

Once daily, early morning. No cron, no reminders — the dashboard still
works, but only when you open it. Pick ONE:

  4a. COMMAND CRON — use this one. Hostinger gives you a command field on
      essentially every plan. No HTTP timeout, no token to leak.

  [ ] Get your absolute path: hPanel -> Files -> File Manager, open the
      folder you uploaded to, read the breadcrumb. Looks like
          /home/u481203847/domains/yourdomain.com/public_html/crm
  [ ] hPanel -> Advanced -> Cron Jobs -> command to run:
          /usr/bin/php <YOUR PATH>/tools/cron-reminders.php
  [ ] Schedule: once a day. Hour 6, minute 0 is fine.
      >> The scheduler runs on SERVER time, often UTC, not your
         configured timezone. Harmless — the app works out "today" from
         its own setting — but 06:00 UTC lands at 1am Central. Use 12:00
         UTC for a ~6-7am Central delivery.
  [ ] Leave 'cron' => 'token' EMPTY (the default), so public/cron.php
      refuses everything and there's no second, unwatched way in
  [ ] TEST IT NOW: set the schedule a few minutes out and wait. Hostinger
      emails you whatever the job prints, and it exits non-zero if a send
      failed. With nothing due it reports zero — which still proves the
      path and the PHP binary. Then set it back to daily.
      >> A wrong path fails loudly: "No such file or directory".

  4b. URL FETCH (plans that only offer a URL)
  [ ] php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
  [ ] Put it in config.php as 'cron' => array('token' => '...')
  [ ] Point the scheduler at https://crm.example.com/cron.php?token=...
      >> THAT URL IS A PASSWORD. It sits in the scheduler config and in
         the fetcher's logs in plain text.
      >> Bad token gets a 404, not a 403 — a 403 confirms it exists.

  No SSH and need to run a tools/ script once? Copy it into public/,
  visit it, DELETE IT AGAIN. (They all refuse to run outside the CLI, so
  a forgotten copy is inert — delete it anyway.)


5. IMPORT LIMITS — TWO NUMBERS THAT MUST AGREE
----------------------------------------------

      config.php  'import' => 'max_upload_mb'   default 10
      PHP         upload_max_filesize           often 2M on shared hosting

  >> The smaller wins, and it's PHP's. A config value above the PHP limit
     is a lie printed on the Import screen.

  [ ] Either raise PHP's (hPanel -> Advanced -> PHP Configuration; 16M is
      plenty) or lower max_upload_mb to match reality
  [ ] Raise post_max_size WITH IT, at least as large
      >> Over upload_max_filesize returns an error the app can report.
         Over post_max_size arrives with $_FILES and $_POST both empty
         and no error code: the form appears submitted, nothing happens.

  Why files are big: a 400-contact export can be 30 MB of which 29 MB is
  photos. The app drops them at parse time; they're still in the upload.


6. CHECK IT
-----------

  [ ] Visit the site -> you get the LOGIN screen
      >> Get the app instead? The hash isn't set. Back to step 2.

  Then on your PHONE (the only device this was built for):

  [ ] add a person with a birthday  -> Today shows it 7 days before
  [ ] tap a row's text              -> edits in place
  [ ] tap "Logged today"            -> reminder resets, row leaves Today
  [ ] swipe a gift idea left        -> deletes, 5 seconds to undo
  [ ] import a .vcf                 -> drafts stage for review, one tap each

  Two behaviours that are decisions, not bugs:
  - People are NOT swipe-deletable. Deleting a person is a button on the
    profile with a confirm. A five-second undo is not enough for years of
    contact history.
  - A reach-out stays overdue until you log a contact. The cron emails
    once and does not move the due date, so the day count climbs.


7. HOME SCREEN
--------------

  [ ] Add via Apple Shortcuts, same as the other apps. No PWA, no service
      worker, deliberately.


NOT IN THIS BUNDLE
------------------

Tests, fixtures, docs/ and CLAUDE.md — none run on the server; they live
in git. config.php is excluded and the build refuses to run if it appears
here.

lib/vendor/PHPMailer IS included: 3 plain files, v6.9.3, required
directly. No Composer, nothing to install.


VERIFIED ONLY ON THE SERVER
---------------------------

Two things cannot be tested in the build environment, so step 1 and step
3 are their real test:

  - schema.sql against a real MySQL (the suite runs against a SQLite
    translation — it proves the logic, not MySQL's parser or its utf8mb4
    index lengths). A rejection names the exact line and will be a syntax
    detail, not a design problem.
  - A real email leaving the app.
